## Owner Approval Gate *(Constitution Principles V, VI, VII, XI & Governance)*

- **Constitution v2.0.0 Amendment (Ratified 2026-10-28, commit `262ecff`)**: The owner has approved and landed the Constitution v2.0.0 amendment to Principles IV, VII, and XI:
  - **Principle XI (Asset Pipeline)**: World assets are low-poly in real-world proportions with one bevel segment on silhouette edges; round parts may be smooth-shaded while hard edges stay sharp. Every world mesh uses the theme's `1,024 x 1,024` px gradient atlas (all themes sharing the exact same UV layout, generated by script from `docs/design/tokens.json`), with each face's UVs inside one atlas cell or one trim strip and one material per mesh. World assets never use `SurfaceAppearance`/PBR maps, transparency, or per-prop lights (`Material.Neon` is used for glow). Ball skins (006a/006b) may use their own `<= 512` px texture; toppers use the world atlas.
  - **Principle VII (Content Is Data)**: A world's theme is pure content data (palette atlas, lighting, weather, music, dressing slots, overlays, hero variants, and a collection-book page), chosen by ID in data and switched by release—never by code changes or player-visible date/countdown checks.
- **Provisional Stylised-Real Triangle Budgets (2026-10-28)**: `Config.Budgets.meshTriangles` is updated from `{ 300, 300, 800, 2500, 2500 }` to the provisional stylised-real budgets `{ 500, 700, 1500, 3500, 5000 }` for Tiers 1–5 (`docs/design/06-art-style.md`, `docs/design/05-roblox-limits.md`). These numbers ship behind this feature and are locked permanently only after Feature 004e's measured capture on the reference phone at full Downtown density with 12 balls and the Holiday overlays.
- **Release-Driven Theme Switching (Confirmed Owner Decision, 2026-10-28)**: Switching the active theme of a world (e.g., Holiday City `winter` to Sunny City `city`) is performed by changing the active theme ID in content data and shipping a release—never via code branches or a live date check/countdown shown to players (Constitution Principles V & VII).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Data-Only Season Re-Theming of a Single Level (Priority: P1)

Instead of splitting a small launch player base across separate seasonal maps, a world level is authored once and re-themed by season (`winter`, `city`, `spring`, `autumn`, `toon`, `neon`) solely by changing its active theme ID in content data. When the active theme ID changes between `winter` (Holiday City) and `city` (Sunny City) on the existing world layout:
- **Palette & Surface Recolouring (Pattern 1 & Pattern 5)**: All imported `MeshPart` props swap `MeshPart.TextureID` to the active theme's `1,024 x 1,024` px gradient atlas, while plain `Part` ground/environment blocks (`SmoothPlastic`) and stand-in fallback parts take their `Part.Color` from the active theme's corresponding `w-*` colour token so even grey-box/stand-in layouts immediately reflect the active season.
- **Dressing Slots (Pattern 2)**: Placements authored as seasonal slots (`slot.small`, `slot.medium`, `slot.yard`, `slot.street`, `slot.landmark`, accounting for at most 15% of total world placements) automatically resolve to the active theme's assigned object types.
- **Theme Overlays & Hero Variants (Pattern 2b)**: Theme-specific overlay zones and fixed placements are added on top of the base layout (within the level's placement budget and clear of gates, shortcuts, markers, and landmark sightlines), and base hero props mapped in `heroVariants` swap to their themed mesh variant while preserving tier, size (`±10%`), collision fidelity, and coin value.
- **Weather, Lighting & Music (Pattern 3)**: Scene lighting (`ClockTime`, `Brightness`, `Ambient`, `OutdoorAmbient`, `FogColor`, `FogStart`, `FogEnd`, and `Atmosphere` from `light-sky`, `light-fog`, `light-ambient`), the looping background music track, and a single camera-attached weather `ParticleEmitter` (capped at `<= 40` active particles and disabled when `Reduce motion` is on) switch to the active theme's configuration.

**Why this priority**: Proves Constitution Principle VII (Content Is Data) and the core architectural premise of the Downtown design system (`docs/design/01-world-kit.md`): one shared 12-player map re-themed by data halves balance/pacing maintenance and makes every subsequent season a zero-code release.

**Independent Test**: Can be verified by toggling the world's `activeThemeId` in data between `"winter"` and `"city"` and running both Lune unit tests and a Studio playtest, confirming that palette texture/colours, lighting, weather emitter, music, all five dressing slot kinds, an overlay zone/placement, and a hero variant switch over with zero code edits in server or client modules and zero new console warnings or errors.

**Acceptance Scenarios**:

1. **Given** a world configured with base zones, fixed placements, five dressing slots (`slot.small`, `slot.medium`, `slot.yard`, `slot.street`, `slot.landmark`), an overlay, and a hero variant, **When** `activeThemeId` is changed from `"winter"` to `"city"` in content data, **Then** the expanded placement set, object templates, `MeshPart.TextureID` (and stand-in/ground `Part.Color`), `Lighting`/`Atmosphere` properties, camera weather emitter, and music track all update to `"city"` without touching any server or client code.
2. **Given** a player has `Reduce motion` enabled in Settings (or toggles it during play), **When** a theme with active weather particles (such as `"winter"` snowfall) is running, **Then** the camera-attached weather `ParticleEmitter` is disabled immediately (`Enabled = false` and cleared), and when `Reduce motion` is off, the emitter never exceeds `40` active particles.
3. **Given** all six themes (`city`, `winter`, `spring`, `autumn`, `toon`, `neon`) defined in `src/shared/Content/Themes.luau` from `docs/design/tokens.json`, **When** Lune content validation tests run, **Then** every theme has a unique `id`, populates all 64 palette cells (32 shared `w-*` roles in rows 0–3 and 32 hero cells in rows 4–7) and all `light-*` lighting properties, and every theme bound to a world resolves every slot, overlay object, and hero variant with valid budgets and clear sightlines/routes.

### User Story 2 - Stylised-Real Gradient Atlas & Blender Export Pipeline (Priority: P1)

Every 3D world prop and theme texture is produced and validated through the updated stylised-real art pipeline (`docs/design/06-art-style.md`, `docs/design/05-roblox-limits.md`, Constitution Principle XI):
- **Deterministic 1,024 px Gradient Atlas per Theme**: `art/scripts/palette.py` reads `docs/design/tokens.json` and deterministically generates one `1,024 x 1,024` px PNG atlas per theme (`city`, `winter`, `spring`, `autumn`, `toon`, `neon`) with an identical layout:
  - **Top half (`1,024 x 512` px)**: 64 palette cells arranged in an `8 x 8` grid (`128 x 64` px per cell; rows 0–3 for the 32 shared `w-*` roles, rows 4–7 for level hero roles), each drawn as a vertical gradient from `+12%` lightness at the cell top to `-15%` lightness at the cell bottom to bake vertical shading and ambient occlusion without lightmaps.
  - **Bottom half (`1,024 x 512` px)**: 8 horizontal trim strips (`1,024 x 64` px each) drawn procedurally in role colours with zero words or logos: grille, vent slats, tyre tread, window frame, brick course, panel seams, kerb stone, and wood grain.
- **Bevelled Silhouette & Split-Normal Export Rules**: Blender prop recipes apply a 1-segment bevel modifier (`4–8%` of object size) on silhouette edges, smooth shading on round parts (cylinders/spheres), and sharp edges on boxy parts. `art/scripts/export_all.py` exports custom/split normals, validates that every mesh has a single `Palette` material and every face's UVs sit inside one atlas cell or one trim strip, and checks triangle counts against the provisional per-tier budgets (`500 / 700 / 1,500 / 3,500 / 5,000`).
- **Mobile-Safe Runtime Mesh Configuration**: Runtime `MeshPart` templates enforce `RenderFidelity = Automatic`, `CollisionFidelity = Box` (Tiers 1–3) or `Hull` (Tiers 4–5), zero `SurfaceAppearance`/PBR instances, zero semi-transparency, and zero per-prop lights (`Material.Neon` on child parts of Tier 4–5 heroes only). A palette QA grid renders a prop across all six themes to verify cross-theme readability.

**Why this priority**: Establishes the asset pipeline required by Constitution Principle XI (v2.0.0) and Principle VI (Mobile First 30 fps) before Feature 004e builds the ~95 Downtown and Holiday City meshes.

**Independent Test**: Can be tested via `scripts/check.sh` and headless Blender verification (`palette.py`, `export_all.py`, and Lune `ArtManifest` / atlas tests), confirming byte-deterministic atlas generation from `tokens.json`, UV cell/strip bounds enforcement, split-normal support, provisional triangle-budget enforcement (`500 / 700 / 1,500 / 3,500 / 5,000`), and a `>= 30 fps` Studio capture at `640 x 360`.

**Acceptance Scenarios**:

1. **Given** `docs/design/tokens.json`, **When** the atlas generator runs twice in succession, **Then** it produces byte-identical `1,024 x 1,024` px PNG atlases for all six themes (`city`, `winter`, `spring`, `autumn`, `toon`, `neon`) and a `palette.json` UV map listing all 64 gradient cells (`128 x 64` px each, `+12%` to `-15%` vertical lightness gradient) and all 8 trim strips (`1,024 x 64` px each).
2. **Given** a Blender mesh collection with a 1-segment silhouette bevel, smooth-shaded round faces, sharp box edges, and UVs placed within atlas cells or trim strips, **When** `art/scripts/export_all.py` runs, **Then** the export succeeds with split normals preserved; conversely, if any face's UVs cross cell/strip boundaries, use more than one material, or exceed `Config.Budgets.meshTriangles[tier]` (`500 / 700 / 1,500 / 3,500 / 5,000`), `export_all.py` exits non-zero with a descriptive error.
3. **Given** a world loaded in Roblox Studio with themed meshes and stand-in parts, **When** inspected at runtime and captured at `640 x 360`, **Then** every world `MeshPart` has `RenderFidelity = Enum.RenderFidelity.Automatic`, zero `SurfaceAppearance` or per-prop light descendants exist, all visible world parts have `Transparency = 0`, and frame rate holds at least `30 fps`.

### User Story 3 - Returning Seasonal Collection-Book Pages Without FOMO (Priority: P2)

Each theme that introduces theme-only objects (seasonal dressing slot objects and overlay-only objects, such as Holiday City's festive props) defines its own Collection Book page (`bookPage`). When that theme is active, players discover its objects and fill the page just like tier pages. When the world switches to another theme (for example, switching from `winter` to `city` in January), the inactive theme's book page remains visible in the Collection Book with all discovered entries and progress intact, labelled as a returning seasonal page (never "limited" and never showing a countdown timer).

**Why this priority**: Fulfils Constitution Principle V (Ethical Monetization: no countdown pressure, no fake "limited" stock) and Principle VII (Content Is Data) so players never lose or feel pressured over seasonal collection progress.

**Independent Test**: Can be tested in Lune unit tests (`tests/unit/Book.test.luau`) and in Studio (`BookUi`) by recording discovered entries on a theme's book page, switching `activeThemeId` from `"winter"` to `"city"`, and verifying that the `"winter"` book page still appears in `Book.pages(...)` and `BookUi` with preserved `collectedCount / totalCount` and a localised returning-season note.

**Acceptance Scenarios**:

1. **Given** a world with a `"winter"` theme that defines a `bookPage` containing theme-only objects, **When** a player absorbs one of those theme-only objects during a `"winter"` run, **Then** the object's `bookId` is recorded in the player's profile book and increments the `"winter"` theme page's `collectedCount`.
2. **Given** a player has discovered objects on the `"winter"` theme page and the world's `activeThemeId` is switched to `"city"`, **When** the player opens the Collection Book, **Then** the `"winter"` theme page remains visible and navigable with its discovered entries and progress preserved, displays a localised returning status label (with zero countdown timers or "limited" wording), and never blocks completion of the base world's tier pages.

### Edge Cases

- **Base Tier Book Pages vs. Theme-Only Objects**: Base world tier pages (Tiers 1–5) MUST count only base kit objects so a player joining in `city` (Sunny City) can still reach 100% completion on Tiers 1–5 without needing `winter`-only objects; theme-only objects (slot objects and overlay objects) belong exclusively to their theme's `bookPage`.
- **Hero Variant Absorption & Book Attribution**: When a theme replaces a base hero with a `heroVariant` (e.g., Donut Food Truck -> Cocoa Truck mesh), absorbing the variant MUST award the same `tier`, `size`, and `coins` as the base hero and credit the base hero's `bookId` (plus the theme page's entry if the variant is also listed on the theme page) so base tier progression and book completion remain identical across themes.
- **Overlay Keep-Out Validation**: If a theme overlay zone or fixed placement encroaches on a declared ring gate, small-only shortcut corridor, booster/trap marker spot, or a spawn point's sightline corridor to a Tier 5 landmark, Lune validation MUST fail immediately at test time (`scripts/check.sh`) before the layout can ship.
- **Missing or Unuploaded Theme Atlas Fallback**: When a theme's `paletteAsset` in `src/shared/Assets.luau` is `""` (not yet uploaded to Roblox) or fails to load in offline/Edit environments, `ObjectVisual` and `WorldBuilder` MUST fall back cleanly without errors, colouring stand-in parts and environment blocks directly from the active theme's `w-*` RGB values in content data.
- **UV Boundary Precision on Gradient Cells**: Because adjacent cells in the `1,024 x 1,024` atlas have different colours and vertical gradients, face UVs placed right on the pixel border of a `128 x 64` cell could bleed into a neighbour under bilinear texture filtering; the atlas UV mapper and `export_all.py` validator MUST inset usable cell UVs by at least a half-texel (`>= 1` px / `~0.001` UV margin) inside each cell or trim strip.

### Key Entities

- **ThemeDef**: Pure content definition of a season/visual theme (`id`, `nameKey`, `paletteAssetKey`, `palette` with 64 cells, `lighting`, `weather`, `musicAssetKey`, `slots`, `overlays`, `heroVariants`, `bookPage`).
- **GradientAtlas (`art/atlases/<themeId>.png`, `art/palette.json`)**: A `1,024 x 1,024` px texture shared by all world meshes in a theme, divided into 64 vertical-gradient swatch cells (`128 x 64` px each, `+12%` to `-15%` lightness) in the top half and 8 procedural trim strips (`1,024 x 64` px each) in the bottom half.
- **DressingSlot (`slot.small`, `slot.medium`, `slot.yard`, `slot.street`, `slot.landmark`)**: A world placement placeholder whose concrete `objectId` is resolved by the active theme (`<= 15%` of total placements).
- **ThemeOverlay (`overlays.zones`, `overlays.fixedPlacements`)**: Theme-specific extra zones and fixed placements layered onto a world's base layout within the placement budget and outside all `keepOutAreas`.
- **HeroVariant**: A theme-specific mapping from a base hero `objectId` to an alternate mesh `assetKey` with identical gameplay stats (`tier`, `coins`, collision class, and `size` within `±10%`).
- **ThemeBookPage (`bookPage`)**: A Collection Book page dedicated to a theme's seasonal objects that remains visible with saved progress and a "returning" status when the theme is inactive.
