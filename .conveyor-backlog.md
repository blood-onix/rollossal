## spec: 001: Grey-box prototype: ball control, absorb, growth, camera
<!-- id: daa78c3e; feature: 001-grey-box-prototype -->

Build the first playable grey-box of Rollossal: one rolling ball per player that sticks to anything small enough, grows by volume, and has a camera that pulls back as it grows. One room with 30 cubes in 4 sizes. The goal is a fun test with 6 people, and proof that the core physics (a growing sphere with welded parts) works without jitter. Design brief: README.md §3.1, §3.2, §12 (risks). Constitution: I, II, III, VI, X, XII.

This is the gate feature: under constitution principle I, no art, monetization or live-ops work may start until this build has been playtested and the owner has signed off.

### Part A: repository foundations (land first, in this branch)
The repo has Spec Kit, Wally packages and Rokit pins, but no source tree yet. Set up:
- Fix the leftovers from another project: wally.toml package name (now `rollossal/rollossal`) and rokit.toml comments (now name Rollossal and cite specs/001-grey-box-prototype).
- Rojo project (`default.project.json`, Rojo 7.7.1): src/shared → ReplicatedStorage.Shared, src/server → ServerScriptService, src/client → StarterPlayer.StarterPlayerScripts, plus Packages/ServerPackages/DevPackages.
- `stylua.toml`, `selene.toml` (Roblox std), `.luaurc` with strict mode; every Luau file starts with `--!strict`.
- `scripts/check.sh`: StyLua check, Selene, luau-lsp analyze, Lune unit tests, and a grep that fails if a forbidden identifier appears under src/shared/Rules (Instance, workspace, game, task, math.random, os.clock, os.time, tick, DateTime, Vector3, CFrame, any service). Resolves constitution TODO(CHECK_SCRIPT).
- A Lune test runner for tests/unit and a Jest-Lua bootstrap for tests/studio.
- A GitHub Actions workflow that runs scripts/check.sh on every pull request.
- Move the design brief to `docs/rollossal-gdd.md` and leave a short README with a link (resolves TODO(GDD_PATH); the constitution already points there).

### Part B: pure rules (src/shared/Rules, Lune-tested with fixed expected values)
- Absorb rule: absorbable if `size ≤ absorbRatio × ballDiameter` (absorbRatio 0.4, proposed). Test the boundary (equal passes, just above fails).
- Growth by volume: `newD = (D³ + k · size³)^(1/3)`, k = 0.6 (proposed). Also the inverse, for knock-offs: removing stuck objects shrinks the ball by their volume, never below the start diameter.
- Speed: grows with diameter^0.5, capped. Camera distance: 4 × diameter, clamped.
- Expected values in tests are hand-computed, never produced by the code under test.

### Part C: config (src/shared/Config)
All tuning numbers and budgets live here, not in scripts: startDiameter 2, absorbRatio 0.4, growthK 0.6, maxVisibleStuck 30, knockOffCount 3, bumpSpeedThreshold, absorbRateLimit 10/s, absorbDistanceTolerance, speed exponent and cap, max server-accepted ball speed, camera multiplier and clamp, jump impulse. Also a feature-flag table (constitution VII) and the budgets from principle VI (visible stuck objects per ball, active parts per server, triangles per mesh).

### Part D: server
- BallService: spawns a `Part` with `Shape = Ball` per player, gives the client network ownership, and sanity-checks speed every heartbeat against Config (correct or reset out-of-range movement; log the violation).
- AbsorbService: one RemoteEvent that accepts only an object ID. Type-check the argument, then validate: the object exists and is not taken; distance ≤ ballRadius + size/2 + tolerance; the size rule passes; the player is under the rate limit. On success the server applies growth, marks the object taken, and publishes the authoritative diameter (for example as an attribute). The client never sends sizes, scores or diameters.
- Bumping: an object above absorb size is a solid obstacle. A hit faster than the bump threshold knocks off the 3 most recent stuck objects, which scatter and can be re-collected, and the ball shrinks by their volume. The server decides; the plan chooses how hits are detected (server-side touch plus relative speed, or a client report the server verifies).
- Simple respawn so the 30-cube room does not run dry during a 6-person test (the "out of sight" rule and pooling come in feature 004).

### Part E: client
- BallController: input from `Humanoid.MoveDirection` (thumbstick or WASD), applied as torque through an `AngularVelocity` constraint plus a small forward force. The avatar is hidden and the player *is* the ball; if the character is removed, read the move vector from the PlayerModule ControlModule instead (plan decides).
- Jump: a small hop for kerbs and stairs. A large on-screen button on mobile (at least 96 px), Space on PC.
- CameraController: follows the ball; distance follows the diameter with smoothing.
- StuckVisuals: welds the object at the contact point with `CanCollide = false` and `Massless = true`. Only the 30 most recent stay visible; older ones count as buried and are removed.

### Part F: grey-box room
One room with 30 cubes in 4 sizes. The plan picks sizes and counts from the growth formula so each size becomes absorbable in turn within a couple of minutes, and shows the maths. If 30 cubes cannot complete the chain, use respawns or more cubes and record why. Plain parts, no art.

### Risks to prove in this feature
- Jitter from resizing a rolling sphere with welded parts (README §12). Measure it. If welding jitters, switch to the fallback: stuck objects are client-side visuals that follow the ball and are not welded. Record the result in the plan.
- Speed exploits from client-owned physics: covered by the server speed check.

### Tests
- tests/unit (Lune): absorb rule, growth and shrink maths, speed and camera curves, Config sanity (numbers positive, caps above minimums).
- tests/studio (Jest-Lua): absorb validation rejects a missing object, an already-taken object, an out-of-range distance, a too-large object, a non-string or unknown ID, and the 11th request in one second.

### Playtest (constitution I)
`specs/<feature>/playtest.md`: date, commit, participant counts per age group (at least 3 adults and 3 children aged 10–12; children by age group only, never by name), findings and the owner's sign-off. Measure: first object rolled up within 5 seconds, jitter, does growth feel satisfying, frame rate on a phone.

### Acceptance
- scripts/check.sh exits 0 locally and in CI.
- Up to 12 players can each roll their own ball in one server; 6 have played together.
- Every absorb goes through server validation; nothing about size comes from the client.
- A knock-off scatters 3 objects that can be re-collected, and the ball shrinks.
- No new console errors or warnings in a Studio playtest driven through the Studio MCP server.

### Out of scope
Run timer, stars and results (002); saving (003); art, audio, VFX and UI styling (004 and later); merging (005).

### Open questions (owner)
- The mid-range reference phone for the 30 fps budget (constitution TODO(REFERENCE_PHONE)).
- The bump speed threshold (tune in the playtest).

## spec: 002: Run loop: timer, tiers, stars, results, Roll again
<!-- id: 902159ef; feature: 002-run-loop -->

Turn free rolling into 4-minute runs with a clear ending: a personal timer, size tiers that unlock as the ball grows, a target with 1–3 stars, a results screen and a one-tap Roll again. This makes the 5-second, 1-minute and one-run loops of the design brief real. Design brief: README.md §2 (core loop, run flow), §3.3 (tiers and targets), §4 (HUD, results). Constitution: II, III, IV (runs with clear endings), VI, VII, IX. Depends on 001.

### Rules (src/shared/Rules, Lune-tested)
- Stars: 1 star at 20 studs, 2 at 45, 3 at 80 (proposed, in Config). Test the boundaries (19.99 → 0 stars, 20 → 1, 45 → 2, 80 → 3).
- Tier lookup: given a diameter and a world's tier table, return the current tier and the next tier's threshold.
- Coin reward: the sum of the `coins` value of every object absorbed in the run, then multipliers passed in as arguments (friend bonus, 2x Coins and Friend Boost pass arrive in 005 and 006; the order they apply in is defined here and tested). Coins are only ever added; knock-offs never take coins away (proposed; confirm in clarify).

### Content (src/shared/Content)
- A tier table per world as data: tier number, name key, diameter range and a "headline" object for the banner. For now, the grey-box room's 4 tiers; Snow Village's real tiers (README §3.3) come in 004 and must need no code change.

### Server: RunManager
- Each player has a personal run with a 4:00 timer (runDurationSeconds = 240 in Config). The server owns the timer and the result; the client only displays it.
- On spawn the run starts immediately. When the bell rings: the ball stops, and the server computes the final diameter, stars, coins earned, the object types collected for the first time this run, and the best final size among the player's Roblox friends in the server (`Player:IsFriendsWith`, cached).
- Roll again: resets the ball to start size at a spawn point and starts a new run in about 3 seconds, in the same server with the same friends. Back to hub: moves the player to a hub area in the same place (a simple grey-box plaza for now; the real hub art comes in 004).
- Edge cases: the player leaves mid-run (the run is dropped; nothing is granted), falls out of the world (respawn at their current size), or the server shuts down mid-run.
- Results are published once per run; any later persistence (003) must be able to apply them exactly once, so each run carries a unique run ID.

### Client: HUD and results (phone first)
- Top centre: timer (mm:ss) and the target size with star markers.
- Top left: size meter, the diameter as a large number plus a bar to the next tier, and "Next: [silhouette] CATS".
- Centre, short-lived: the pickup pop "+ Teddy Bear" with an icon (one line, fades in 1 s), and the tier banner "You can roll up: CATS!" while the camera pulls back.
- Feedback: every pickup gets a sound and a scale "pop", a light haptic pulse on mobile (`HapticService`), and camera shake on knock-offs. Grey-box placeholders for sounds and icons are fine here; final audio comes in 004.
- Results screen: final size, stars, coins, new book entries, the friend comparison, a large Roll again and a Back to hub. No discounts, no timers, nothing for sale here yet.
- Readability: text at least 18 px on phones, `UIScale` per viewport, buttons at least 96 px, a dark outline on every text element, and every status shown with an icon and a label (never colour or sound alone).

### Localisation (constitution IX, from day one)
Every player-facing string, including the tier banner and object names, comes from a LocalizationTable kept in the repo. English only in this feature; Spanish is completed in 007. No hard-coded strings in scripts or UI.

### Tests
- Lune: stars, tier lookup, coin reward with and without multipliers.
- Jest-Lua (Studio): the run ends on the server at 240 s even if the client stops sending anything; results are produced once per run ID; a client cannot end a run early or report a size.

### Acceptance
- A player can play three runs in a row with Roll again, each ending with a results screen.
- The HUD and results screen read correctly at a phone resolution (capture the viewport through the Studio MCP server).
- Tier banners appear when the diameter crosses a tier threshold, and only once per tier per run.
- No new console errors or warnings in a Studio playtest.

### Out of scope
Saving coins, best size or the book between sessions (003); party runs and merged balls (005); Shop (006); onboarding hints (007).

### Open questions (owner)
- Whether knock-offs can reduce the coins earned in a run (proposed: no).
- What the "friend comparison" shows when no friends are in the server (proposed: your own best size for this world, once 003 lands).

## spec: 003: Saving and economy: DataService, coins, best size, collection book, settings
<!-- id: 33ce52dc; feature: 003-saving-and-economy -->

Make progress persist: a ProfileStore-backed DataService that saves coins, best size per world, the collection book and settings, plus the Book screen and the Settings screen. Design brief: README.md §3.5 (progression and economy), §4 (collection book, settings), §9 (profile schema v1). Constitution: II, V (one soft currency), VIII (player data), IX. Depends on 002 (run results with run IDs).

### Owner approval required before implementation (constitution VIII, Human Approval)
The DataStore key name and the profile schema key names. The spec proposes them; work stops for the owner's approval before any code writes to a DataStore.

### Profile schema v1 (proposed)
`version`, `coins`, `worldsUnlocked`, `skinsOwned`, `equipped`, `book` (a set of `bookId`s), `bestSize` (per world), `receipts` (processed receipt IDs, used by 006), `settings` (musicVolume, effectsVolume, cameraSensitivity, reduceMotion, language). Only user IDs and game progress are stored; no names, chat or contact details.

### DataService (server, ProfileStore 1.0.3 from wally.toml)
- Load the profile on join with a session lock, reconcile missing fields with defaults, release on leave, and save everything on server shutdown (`BindToClose`).
- If a profile cannot be loaded, kick the player with a friendly, localised message rather than letting them play unsaved.
- A migration table keyed by version: every schema change ships with a migration and a test of that migration. v1 ships with the "new profile" path and a test that a v1 profile loads unchanged.
- Run results from 002 are applied exactly once per run ID (coins added, bestSize raised if beaten, new bookIds added). A repeated or late result grants nothing.
- Use the ProfileStore mock store in Studio tests and in the private test place; never write to the live DataStore from a test.

### Economy
- Coins are the only currency. They are earned only by playing and are never sold (constitution V).
- Best size is kept per world and shown on the results screen and the hub.
- In the MVP only Snow Village exists, so coins have no sink yet. Open question below.

### Collection book
- One entry per object type, grouped by tier into pages. Unknown objects show as silhouettes; each page shows progress (for example 7 / 15).
- Completing a page grants a cosmetic reward defined in content data (a skin or trail ID). The reward mechanism is built here; the reward items themselves arrive with 004 and 006.
- The results screen shows "New in your book" for first-time objects. The first results screen explains the book and coins (the full onboarding pass is 007).
- BookUi: a grid by tier, readable on phones (18 px text, icons with labels), opened from the top-right Book button. It must not open during a run's first seconds or cover the timer.

### Settings screen
Music volume, effects volume, camera sensitivity, Reduce motion (removes camera shake and other strong motion), and language (applied to the LocalizationTable). Saved in the profile and applied on join. Opened from the top-right Settings button.

### Tests
- Jest-Lua (Studio): new profile gets defaults; missing fields are reconciled; run results apply once per run ID; coins never go negative; book entries are a set; best size only increases; the v1 migration test; a failed load kicks rather than playing unsaved.
- Lune: book page progress and page-complete checks as pure functions.

### Acceptance
- Coins, best size, book and settings survive leaving and rejoining (verified in the private test place).
- Two servers cannot both hold the same profile (session lock).
- The Book and Settings screens read correctly at a phone resolution.
- No new console errors or warnings in a Studio playtest.

### Out of scope
Purchases and receipts handling (006), world unlocks and ball cores (011), the daily golden object (012).

### Open questions (owner)
- The DataStore key name and schema key names (approval required).
- A coin sink in the MVP: with one world, coins only accumulate. Options: ship ball cores (Sticky, Heavy, Zoomy; README §3.5) in the MVP, or let coins pile up until Candy Town unlocks in January.

## spec: 005: Co-op: merge and split, friend bonus, party flow
<!-- id: 89459d21 -->

Make Rollossal funny with friends: two friends can merge into one bigger ball, steer it together, and split again; friends earn bonus coins; parties start and repeat runs together. Design brief: README.md §1 (pillar 2), §3.4 (multiplayer), §4 (Merge button). Constitution: II, III, IV, VI, VII (behind a flag). Depends on 002 and 003.

### Rules (src/shared/Rules, Lune-tested)
- Merge: the merged ball's volume is (V1 + V2) × 1.10 (merge bonus 10%, proposed, in Config).
- Split: each player takes half the merged volume.
- Exploit to close: merging and splitting repeatedly would grow both balls by 10% per cycle without rolling anything. The spec must prevent this. Proposed: the bonus applies once per pair per run, plus a merge cooldown (about 10 s). The tests prove that any number of merge-and-split cycles adds at most one merge bonus per pair per run.
- Coins earned while merged are split evenly; the rounding rule is defined and tested.
- Coin multipliers: friend bonus +20% while at least one Roblox friend is in the server (proposed). Its order with 2x Coins and Friend Boost (006) follows the coin rule defined in 002.

### Merge flow
- The Merge button (bottom right, at least 96 px) appears only while touching an eligible player. Both players must tap it within a short window (proposed 3 s); the server checks both requests, the touching distance and the cooldown.
- Eligible: Roblox friends and members of your party (proposed). Strangers cannot merge with you, so nobody can be pulled into a merge.
- Steering is the average of both players' inputs. The plan decides who simulates the merged ball (one player's client owns it and receives the partner's input through the server, or the server owns it) and measures input latency on a phone.
- Absorbs, knock-offs and tiers work as for a single ball. Each player gets every new book entry the merged ball collects (proposed).
- Split: either player taps Split; both balls reappear side by side with half the volume each.
- Timers stay personal. When one player's run ends while merged, the ball splits automatically: that player goes to results, the other keeps playing.

### Party flow
- Invite friends with the built-in Roblox invite prompt (`SocialService`); no typing or chat needed.
- A party starts its runs together with one shared timer, and Roll again keeps the same friends together (README §2: "same friends, about 3 seconds").
- The results screen shows the party's sizes side by side.

### Tests
- Lune: merge and split maths, the once-per-pair bonus, coin splitting and rounding, multiplier order.
- Jest-Lua (Studio): merge needs both players' consent; is refused when not touching, during cooldown or for non-eligible players; remotes accept only intents (no sizes); a player leaving while merged splits the ball cleanly and loses nothing.

### Acceptance
- Two friends can merge, roll up objects together, split, and each keeps half; repeated merge and split cannot inflate size.
- A party of 3 can play three runs in a row with Roll again and stay together.
- Merge and Split are playable with one thumb on a phone (the owner checks on a real phone).
- Behind a feature flag in Config; no new console errors or warnings in a Studio playtest with at least 2 clients.
- Grey-box check of merge before any polish (constitution I): an agent-driven Studio local server with 2 or 3 clients plus the owner playing it, recorded in playtest.md. No outside players are needed for this feature (owner decision, 2026-10-26); merging with real friends is covered by the next people playtest round (004d if 005 lands before it, otherwise the pre-launch round in 008).

### Out of scope
Big Ball mode and player swallowing (009); the Friend Boost game pass purchase (006; its +25% effect for everyone in your merged ball is applied by the coin rule here once 006 reports ownership).

### Open questions (owner)
- Merge with non-friends in the same server: allow or not (proposed: friends and party only).
- Do both merged players get book entries (proposed: yes)?

## spec: 006: Shop and purchases: skins, trails, passes, idempotent receipts, VIP server
<!-- id: b6aa306e -->

Add the fair-and-kind shop: cosmetic ball skins and trails, the 2x Coins and Friend Boost passes, and VIP servers, with an idempotent receipt handler and prices that always come from Roblox. Design brief: README.md §4 (Shop screen), §6 (monetization). Constitution: I (the owner's grey-box sign-off; the playtest with outside people is deferred to 004d, owner decision 2026-10-26), IV, V, VIII. Depends on 003 (profile with skinsOwned, equipped, receipts) and 005 (merged balls, for Friend Boost).

### Owner approval required (constitution V, Human Approval)
Every game pass, developer product and price. Prices are TBD (owner). The owner creates the products in Creator Hub; their IDs go into content data. Agents never set prices.

### Products in the MVP
- Ball skins (5 in the MVP: for example snowglobe, disco, planet): cosmetic only.
- Trails and pickup effects (2 in the MVP): cosmetic only.
- 2x Coins (game pass): doubles coins earned. It never changes size, speed or anything inside a run.
- Friend Boost (game pass): everyone in your merged ball earns +25% coins. A purchase that benefits friends.
- VIP server: Roblox private servers so a group of friends can play on their own.
Never sold: coins, random items, loot boxes, luck boosts, gameplay boosters or perks that help inside a run (the boosters from 004b are only picked up in the world), anything that wins Big Ball mode. No trading.

### PurchaseService (server)
- `ProcessReceipt` is idempotent: if the receipt ID is already in the profile, return PurchaseGranted and grant nothing. Otherwise grant and record the receipt in the same profile update, and return PurchaseGranted only once the profile holds it. If the player's profile is not loaded, return NotProcessedYet.
- Keep the receipts list bounded (for example the most recent N) without breaking idempotency for recent receipts; the spec states N.
- Game pass ownership: `UserOwnsGamePassAsync` on join (cached), updated on `PromptGamePassPurchaseFinished`.
- The coin rule from 002 receives 2x Coins and Friend Boost as inputs; the server decides who owns what.

### Shop screen (client)
- Tabs: Skins, Trails, Passes. Each button shows the price in Robux, read from `MarketplaceService:GetProductInfo` (never hard-coded), and a one-line "what it does".
- Equip and unequip owned skins and trails; others see your equipped skin.
- The Shop is disabled during a run and shows "after this run". It is introduced only from run 2 on (onboarding in 007).
- No countdowns, discounts, fake "limited" stock or pop-up offers during runs. The results screen may show at most one optional, dismissible line about a relevant cosmetic.

### Art
Skins and trails follow the Blender pipeline and palette from 004 (constitution XI); IDs in Assets.luau.

### Safety
Wrap any future paid-item or ad features in `PolicyService` checks. Rewarded video ads and subscriptions are not in the MVP; ads stay behind a flag that is off.

### Tests (tests/studio, Jest-Lua, required by constitution V)
- A repeated receipt grants nothing; two receipts grant twice; a receipt for a player without a loaded profile returns NotProcessedYet; an unknown product ID is rejected and logged.
- 2x Coins doubles coins and never size; Friend Boost applies +25% to every player in the merged ball and stops when they split.
- Prices shown in the UI come from GetProductInfo (test with a stubbed MarketplaceService).

### Acceptance
- Test purchases in Studio and in the private test place grant exactly once, survive rejoining, and equip correctly (the owner runs the private-test-place purchases; no outside players needed).
- The Shop reads correctly at a phone resolution; every button shows a price and a description.
- No new console errors or warnings in a Studio playtest.

### Out of scope
Early world unlock and Auto-book (after MVP), season cosmetic packs (live ops).

### Open questions (owner)
- Prices for every product.
- Skins as game passes or developer products: passes keep ownership with Roblox; developer products need our own record in skinsOwned. Proposed: game passes.

## spec: 007: Onboarding, analytics and localisation (English and Spanish)

## spec: 009: Big Ball mode: opt-in player swallowing
<!-- id: 2e3ef672 -->

After launch (planned for late December): an opt-in mode where a ball 1.3× bigger than another player's ball can swallow it. Never on in the default mode. Design brief: README.md §3.4 (Big Ball mode), §6 (nothing paid wins it), §7. Constitution: IV (opt-in, own mode, no persistent loss; owner approval before work starts because it may change questionnaire answers), V, II.

### Owner approval before work starts
Player-to-player swallowing may change the maturity questionnaire answers. Work does not start without the owner's written approval.

### Mode
- Lives in its own servers (a separate place in the universe, or reserved servers; the plan decides). Players enter only through an explicit choice in the hub with a short explanation of the rules. Never on in the default mode, never a surprise.
- Rule (src/shared/Rules, Lune-tested): a ball can swallow another when its diameter is at least 1.3× the other's (proposed, in Config). Whether the swallower gains the victim's volume, and how much, is defined in the spec (proposed: like an object, with the growth efficiency k).
- The swallowed player respawns small at once, with brief spawn protection (proposed 3 s), and loses no permanent progress: coins and book entries already earned in that run are kept.
- The server validates every swallow (both balls exist, distance, the 1.3× rule, the victim is not protected).
- Fairness: ball cores never apply here; nothing paid changes the outcome (skins and trails are cosmetic; 2x Coins only affects coins after the run). Merging is disabled in this mode (proposed) to avoid teaming.
- Kind design: no kill feed naming players, no taunts; a per-server "biggest ball" board only.
- Behind the `BigBallMode` feature flag.

### Match shape (proposed by the owner, 2026-10-26: "king of the hill")
Unlike the personal runs of the default mode, Big Ball rounds are shared matches with one server timer, so everyone starts and ends together:
- Peaceful phase (proposed first 60 s of a 4-minute round): no swallowing; everyone eats objects and grows. A clear banner and sound announce when it ends (and the HUD shows when swallowing switches on, with an icon and label, not colour alone).
- Swallow phase: the 1.3× rule is live. Boosters and traps from 004b work here too, so a smaller ball can escape or trick a bigger one (for example a dash, a shield or luring it onto ice).
- Hill (optional, plan decides): in the last minute a marked zone (for example the town square) gives bonus growth to the biggest ball standing in it, so the round ends in a fight for the hill rather than hiding.
- The biggest ball at the bell wins the round; the results show the top three sizes, no names in a feed.
- The Rules for phases (which phase is live at time t) are pure functions with time passed in, Lune-tested.

### Tests
- Lune: the swallow threshold at the boundary, volume gained, phase at a given time (peaceful vs swallow vs hill).
- Jest-Lua (Studio): a swallow request is refused below 1.3×, out of range, against a protected player, or during the peaceful phase; a swallowed player keeps their coins and book entries; the default mode never allows a swallow even if a client asks.

### Acceptance
- Grey-box check before polish (constitution I): an agent-driven Studio local server with at least 3 clients plus the owner playing it, recorded in playtest.md with the owner's sign-off. Real players try it in the next people playtest round (owner decision, 2026-10-26: no outside players before the game has art and animation).
- The default mode is provably unaffected.
- No new console errors or warnings in a Studio playtest with at least 3 clients.

### Open questions (owner)
- Separate place or reserved servers.
- Volume gained by swallowing.
- Whether merging is allowed in this mode.
- Peaceful phase length, and whether the hill zone is in.

## spec: 010: Avatar pusher: show the player's avatar pushing the ball
<!-- id: 270546b8 -->

After launch: instead of the player being the ball, their Roblox avatar appears behind the ball with a pushing animation, behind the `AvatarPusher` feature flag. Design brief: README.md §3.1 (avatar). Constitution: I (grey-box check of the new mechanic before polish), II, VI, VII.

### Behaviour
- The avatar stands behind the ball relative to its movement direction and plays a pushing animation whose speed matches the ball's speed; idle when the ball stops; a jump animation on hop.
- Scale: the ball grows from 2 to over 100 studs while the avatar stays human-sized. The spec decides how it stays readable (proposed: the avatar scales up with the ball up to a cap, and the camera framing keeps it in view).

- Merged balls: both avatars push from opposite sides (or the spec chooses another clear layout).
- Works with R15 and R6 avatars; layered clothing and accessories must not break the pose.

### Performance

## spec: 012: Live ops: weekly object drops and the daily golden object
<!-- id: dc2bd70f -->

After launch: weekly content drops in December (8–10 new objects and one new skin per week), the daily golden object, and a weekly golden-object event, all shipped as data. Design brief: README.md §3.5 (daily golden object), §7 (live ops). Constitution: I (needs 001 sign-off), III, IV, V, VII, VIII. Depends on 003 and 004.

### Weekly object drops
- New objects are content data plus assets; no code changes. Each object can carry an `availableFrom` date, so a drop can ship ahead of time and switch on by server date (the date is passed into pure Rules, never read inside them).
- Drops extend the collection book; page progress and page rewards stay correct when a page grows (a completed page that gains entries does not take its reward back).
- A short how-to in the feature folder: the steps to add a drop (Blender, budgets, Assets.luau, content entry, localisation in English and Spanish, validation tests).
- New objects stay in the game after their week: nothing becomes missable forever (pillar 4, "nothing pressures you").

### Daily golden object
- One hidden golden object per world per day, chosen and placed by a seed derived from the UTC date (pure function in src/shared/Rules, Lune-tested: the same date always gives the same choice and spawn point).
- Absorbing it gives bonus coins (value in Config) once per player per day. The server validates it like any absorb.
- Missing a day costs nothing: no streaks, no countdowns, no reminders.
- Storing "claimed today" in the profile is a schema change: owner approval and a migration with a test (constitution VIII).

### Weekly golden-object event
A weekly variant (for example several golden objects for a weekend) defined as dated content data, using the same mechanism.

### Weekly skin
One new cosmetic skin per week through the shop from 006. Each new product and its price needs owner approval.

### Acceptance
- Adding a drop is a data and asset change only; scripts/check.sh exits 0 with the new content.
- The golden object appears in the same place for every server on a given day and can be claimed once per player per day.
- No new console errors or warnings in a Studio playtest.

### Open questions (owner)
