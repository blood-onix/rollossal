## spec: 001: Grey-box prototype: ball control, absorb, growth, camera
<!-- id: daa78c3e; feature: 001-grey-box-prototype -->

Build the first playable grey-box of Rollossal: one rolling ball per player that sticks to anything small enough, grows by volume, and has a camera that pulls back as it grows. One room with 30 cubes in 4 sizes. The goal is a fun test with 6 people, and proof that the core physics (a growing sphere with welded parts) works without jitter. Design brief: README.md §3.1, §3.2, §12 (risks). Constitution: I, II, III, VI, X, XII.

This is the gate feature: under constitution principle I, no art, monetization or live-ops work may start until this build has been playtested and the owner has signed off.

### Part A: repository foundations (land first, in this branch)
The repo has Spec Kit, Wally packages and Rokit pins, but no source tree yet. Set up:
- Fix the leftovers from another project: wally.toml package name (now `rollossal/rollossal`) and rokit.toml comments (now name Rollossal and cite specs/001-grey-box-prototype).
- Rojo project (`default.project.json`, Rojo 7.7.1): src/shared → ReplicatedStorage.Shared, src/server → ServerScriptService, src/client → StarterPlayer.StarterPlayerScripts, plus Packages/ServerPackages/DevPackages.
- `stylua.toml`, `selene.toml` (Roblox std), `.luaurc` with strict mode; every Luau file starts with `--!strict`.
- `scripts/check.sh`: StyLua check, Selene, luau-lsp analyze, Lune unit tests, and a grep that fails if a forbidden identifier appears under src/shared/Rules (Instance, workspace, game, task, math.random, os.clock, os.time, tick, DateTime, Vector3, CFrame, any service). Resolves constitution TODO(CHECK_SCRIPT).
- A Lune test runner for tests/unit and a Jest-Lua bootstrap for tests/studio.
- A GitHub Actions workflow that runs scripts/check.sh on every pull request.
- Move the design brief to `docs/rollossal-gdd.md` and leave a short README with a link (resolves TODO(GDD_PATH); the constitution already points there).

### Part B: pure rules (src/shared/Rules, Lune-tested with fixed expected values)
- Absorb rule: absorbable if `size ≤ absorbRatio × ballDiameter` (absorbRatio 0.4, proposed). Test the boundary (equal passes, just above fails).
- Growth by volume: `newD = (D³ + k · size³)^(1/3)`, k = 0.6 (proposed). Also the inverse, for knock-offs: removing stuck objects shrinks the ball by their volume, never below the start diameter.
- Speed: grows with diameter^0.5, capped. Camera distance: 4 × diameter, clamped.
- Expected values in tests are hand-computed, never produced by the code under test.

### Part C: config (src/shared/Config)
All tuning numbers and budgets live here, not in scripts: startDiameter 2, absorbRatio 0.4, growthK 0.6, maxVisibleStuck 30, knockOffCount 3, bumpSpeedThreshold, absorbRateLimit 10/s, absorbDistanceTolerance, speed exponent and cap, max server-accepted ball speed, camera multiplier and clamp, jump impulse. Also a feature-flag table (constitution VII) and the budgets from principle VI (visible stuck objects per ball, active parts per server, triangles per mesh).

### Part D: server
- BallService: spawns a `Part` with `Shape = Ball` per player, gives the client network ownership, and sanity-checks speed every heartbeat against Config (correct or reset out-of-range movement; log the violation).
- AbsorbService: one RemoteEvent that accepts only an object ID. Type-check the argument, then validate: the object exists and is not taken; distance ≤ ballRadius + size/2 + tolerance; the size rule passes; the player is under the rate limit. On success the server applies growth, marks the object taken, and publishes the authoritative diameter (for example as an attribute). The client never sends sizes, scores or diameters.
- Bumping: an object above absorb size is a solid obstacle. A hit faster than the bump threshold knocks off the 3 most recent stuck objects, which scatter and can be re-collected, and the ball shrinks by their volume. The server decides; the plan chooses how hits are detected (server-side touch plus relative speed, or a client report the server verifies).
- Simple respawn so the 30-cube room does not run dry during a 6-person test (the "out of sight" rule and pooling come in feature 004).

### Part E: client
- BallController: input from `Humanoid.MoveDirection` (thumbstick or WASD), applied as torque through an `AngularVelocity` constraint plus a small forward force. The avatar is hidden and the player *is* the ball; if the character is removed, read the move vector from the PlayerModule ControlModule instead (plan decides).
- Jump: a small hop for kerbs and stairs. A large on-screen button on mobile (at least 96 px), Space on PC.
- CameraController: follows the ball; distance follows the diameter with smoothing.
- StuckVisuals: welds the object at the contact point with `CanCollide = false` and `Massless = true`. Only the 30 most recent stay visible; older ones count as buried and are removed.

### Part F: grey-box room
One room with 30 cubes in 4 sizes. The plan picks sizes and counts from the growth formula so each size becomes absorbable in turn within a couple of minutes, and shows the maths. If 30 cubes cannot complete the chain, use respawns or more cubes and record why. Plain parts, no art.

### Risks to prove in this feature
- Jitter from resizing a rolling sphere with welded parts (README §12). Measure it. If welding jitters, switch to the fallback: stuck objects are client-side visuals that follow the ball and are not welded. Record the result in the plan.
- Speed exploits from client-owned physics: covered by the server speed check.

### Tests
- tests/unit (Lune): absorb rule, growth and shrink maths, speed and camera curves, Config sanity (numbers positive, caps above minimums).
- tests/studio (Jest-Lua): absorb validation rejects a missing object, an already-taken object, an out-of-range distance, a too-large object, a non-string or unknown ID, and the 11th request in one second.

### Playtest (constitution I)
`specs/<feature>/playtest.md`: date, commit, participant counts per age group (at least 3 adults and 3 children aged 10–12; children by age group only, never by name), findings and the owner's sign-off. Measure: first object rolled up within 5 seconds, jitter, does growth feel satisfying, frame rate on a phone.

### Acceptance
- scripts/check.sh exits 0 locally and in CI.
- Up to 12 players can each roll their own ball in one server; 6 have played together.
- Every absorb goes through server validation; nothing about size comes from the client.
- A knock-off scatters 3 objects that can be re-collected, and the ball shrinks.
- No new console errors or warnings in a Studio playtest driven through the Studio MCP server.

### Out of scope
Run timer, stars and results (002); saving (003); art, audio, VFX and UI styling (004 and later); merging (005).

### Open questions (owner)
- The mid-range reference phone for the 30 fps budget (constitution TODO(REFERENCE_PHONE)).
- The bump speed threshold (tune in the playtest).

## spec: 002: Run loop: timer, tiers, stars, results, Roll again
<!-- id: 902159ef; feature: 002-run-loop -->

Turn free rolling into 4-minute runs with a clear ending: a personal timer, size tiers that unlock as the ball grows, a target with 1–3 stars, a results screen and a one-tap Roll again. This makes the 5-second, 1-minute and one-run loops of the design brief real. Design brief: README.md §2 (core loop, run flow), §3.3 (tiers and targets), §4 (HUD, results). Constitution: II, III, IV (runs with clear endings), VI, VII, IX. Depends on 001.

### Rules (src/shared/Rules, Lune-tested)
- Stars: 1 star at 20 studs, 2 at 45, 3 at 80 (proposed, in Config). Test the boundaries (19.99 → 0 stars, 20 → 1, 45 → 2, 80 → 3).
- Tier lookup: given a diameter and a world's tier table, return the current tier and the next tier's threshold.
- Coin reward: the sum of the `coins` value of every object absorbed in the run, then multipliers passed in as arguments (friend bonus, 2x Coins and Friend Boost pass arrive in 005 and 006; the order they apply in is defined here and tested). Coins are only ever added; knock-offs never take coins away (proposed; confirm in clarify).

### Content (src/shared/Content)
- A tier table per world as data: tier number, name key, diameter range and a "headline" object for the banner. For now, the grey-box room's 4 tiers; Snow Village's real tiers (README §3.3) come in 004 and must need no code change.

### Server: RunManager
- Each player has a personal run with a 4:00 timer (runDurationSeconds = 240 in Config). The server owns the timer and the result; the client only displays it.
- On spawn the run starts immediately. When the bell rings: the ball stops, and the server computes the final diameter, stars, coins earned, the object types collected for the first time this run, and the best final size among the player's Roblox friends in the server (`Player:IsFriendsWith`, cached).
- Roll again: resets the ball to start size at a spawn point and starts a new run in about 3 seconds, in the same server with the same friends. Back to hub: moves the player to a hub area in the same place (a simple grey-box plaza for now; the real hub art comes in 004).
- Edge cases: the player leaves mid-run (the run is dropped; nothing is granted), falls out of the world (respawn at their current size), or the server shuts down mid-run.
- Results are published once per run; any later persistence (003) must be able to apply them exactly once, so each run carries a unique run ID.

### Client: HUD and results (phone first)
- Top centre: timer (mm:ss) and the target size with star markers.
- Top left: size meter, the diameter as a large number plus a bar to the next tier, and "Next: [silhouette] CATS".
- Centre, short-lived: the pickup pop "+ Teddy Bear" with an icon (one line, fades in 1 s), and the tier banner "You can roll up: CATS!" while the camera pulls back.
- Feedback: every pickup gets a sound and a scale "pop", a light haptic pulse on mobile (`HapticService`), and camera shake on knock-offs. Grey-box placeholders for sounds and icons are fine here; final audio comes in 004.
- Results screen: final size, stars, coins, new book entries, the friend comparison, a large Roll again and a Back to hub. No discounts, no timers, nothing for sale here yet.
- Readability: text at least 18 px on phones, `UIScale` per viewport, buttons at least 96 px, a dark outline on every text element, and every status shown with an icon and a label (never colour or sound alone).

### Localisation (constitution IX, from day one)
Every player-facing string, including the tier banner and object names, comes from a LocalizationTable kept in the repo. English only in this feature; Spanish is completed in 007. No hard-coded strings in scripts or UI.

### Tests
- Lune: stars, tier lookup, coin reward with and without multipliers.
- Jest-Lua (Studio): the run ends on the server at 240 s even if the client stops sending anything; results are produced once per run ID; a client cannot end a run early or report a size.

### Acceptance
- A player can play three runs in a row with Roll again, each ending with a results screen.
- The HUD and results screen read correctly at a phone resolution (capture the viewport through the Studio MCP server).
- Tier banners appear when the diameter crosses a tier threshold, and only once per tier per run.
- No new console errors or warnings in a Studio playtest.

### Out of scope
Saving coins, best size or the book between sessions (003); party runs and merged balls (005); Shop (006); onboarding hints (007).

### Open questions (owner)
- Whether knock-offs can reduce the coins earned in a run (proposed: no).
- What the "friend comparison" shows when no friends are in the server (proposed: your own best size for this world, once 003 lands).

## spec: 003: Saving and economy: DataService, coins, best size, collection book, settings
<!-- id: 33ce52dc; feature: 003-saving-and-economy -->

Make progress persist: a ProfileStore-backed DataService that saves coins, best size per world, the collection book and settings, plus the Book screen and the Settings screen. Design brief: README.md §3.5 (progression and economy), §4 (collection book, settings), §9 (profile schema v1). Constitution: II, V (one soft currency), VIII (player data), IX. Depends on 002 (run results with run IDs).

### Owner approval required before implementation (constitution VIII, Human Approval)
The DataStore key name and the profile schema key names. The spec proposes them; work stops for the owner's approval before any code writes to a DataStore.

### Profile schema v1 (proposed)
`version`, `coins`, `worldsUnlocked`, `skinsOwned`, `equipped`, `book` (a set of `bookId`s), `bestSize` (per world), `receipts` (processed receipt IDs, used by 006), `settings` (musicVolume, effectsVolume, cameraSensitivity, reduceMotion, language). Only user IDs and game progress are stored; no names, chat or contact details.

### DataService (server, ProfileStore 1.0.3 from wally.toml)
- Load the profile on join with a session lock, reconcile missing fields with defaults, release on leave, and save everything on server shutdown (`BindToClose`).
- If a profile cannot be loaded, kick the player with a friendly, localised message rather than letting them play unsaved.
- A migration table keyed by version: every schema change ships with a migration and a test of that migration. v1 ships with the "new profile" path and a test that a v1 profile loads unchanged.
- Run results from 002 are applied exactly once per run ID (coins added, bestSize raised if beaten, new bookIds added). A repeated or late result grants nothing.
- Use the ProfileStore mock store in Studio tests and in the private test place; never write to the live DataStore from a test.

### Economy
- Coins are the only currency. They are earned only by playing and are never sold (constitution V).
- Best size is kept per world and shown on the results screen and the hub.
- In the MVP only Snow Village exists, so coins have no sink yet. Open question below.

### Collection book
- One entry per object type, grouped by tier into pages. Unknown objects show as silhouettes; each page shows progress (for example 7 / 15).
- Completing a page grants a cosmetic reward defined in content data (a skin or trail ID). The reward mechanism is built here; the reward items themselves arrive with 004 and 006.
- The results screen shows "New in your book" for first-time objects. The first results screen explains the book and coins (the full onboarding pass is 007).
- BookUi: a grid by tier, readable on phones (18 px text, icons with labels), opened from the top-right Book button. It must not open during a run's first seconds or cover the timer.

### Settings screen
Music volume, effects volume, camera sensitivity, Reduce motion (removes camera shake and other strong motion), and language (applied to the LocalizationTable). Saved in the profile and applied on join. Opened from the top-right Settings button.

### Tests
- Jest-Lua (Studio): new profile gets defaults; missing fields are reconciled; run results apply once per run ID; coins never go negative; book entries are a set; best size only increases; the v1 migration test; a failed load kicks rather than playing unsaved.
- Lune: book page progress and page-complete checks as pure functions.

### Acceptance
- Coins, best size, book and settings survive leaving and rejoining (verified in the private test place).
- Two servers cannot both hold the same profile (session lock).
- The Book and Settings screens read correctly at a phone resolution.
- No new console errors or warnings in a Studio playtest.

### Out of scope
Purchases and receipts handling (006), world unlocks and ball cores (011), the daily golden object (012).

### Open questions (owner)
- The DataStore key name and schema key names (approval required).
- A coin sink in the MVP: with one world, coins only accumulate. Options: ship ball cores (Sticky, Heavy, Zoomy; README §3.5) in the MVP, or let coins pile up until Candy Town unlocks in January.

## spec: 004b: Mechanics pass: a jump that matters, boosters and traps
<!-- id: 06587a07 -->

Make the default mode richer before it gets polish and before people test it. Owner feedback (2026-10-26): "jump is useless, you cannot jump over the obstacles or boxes", and the game needs boosters and traps so players can trick each other. Design brief: docs/rollossal-gdd.md §3.1 (ball control), §3.2 (bumping); design system: docs/design/03-city-level.md (layout rules), 01-world-kit.md (slots). Constitution: I (grey-box first), II, III, IV, VI, VII (every booster and trap behind a flag). Depends on 004. Grey-boxed on Snow Village; 004e (Downtown) places the boosters and traps from the marker spots this feature defines.

### Jump
- Today the hop is a fixed small impulse and clears nothing. The jump height scales with the ball's diameter so the ball can always hop over an obstacle it cannot absorb yet (proposed: clear an object about 0.6 × the diameter tall, just above absorb size). Jump height from diameter is a pure rule in src/shared/Rules, Lune-tested; impulse values in Config.
- Downtown needs it from the first second: kerbs and stoops need the jump at tier 1, and the Car Park spiral ramp and the Construction Site's scaffolding and container stack are climbing routes (docs/design/03-city-level.md "Something to climb").
- Ground check and a short cooldown, so jumps cannot be chained into flight.
- The server's movement checks know about vertical velocity and jump height (today the anti-teleport check is horizontal only), so a legit jump is never corrected and a fake one is.
- Plan decides on a charged jump (hold to jump higher); it must stay playable with one thumb, Jump button still at least 96 px (`touch-main`).
- Grey-box feedback: a landing thump and a simple squash on landing (placeholder; polish in 004c).

### Boosters (world pickups, respawning, content data)
Proposed starter set; each has its values in Config and its own flag:
- Dash pad / Dash pickup: a short speed burst. The server speed check has an explicit boost cap so a boosted ball is not reset and a cheating one still is.
- Magnet: for a few seconds, nearby absorbable objects drift toward the ball (the server still validates each absorb).
- Spring / ramp: launches the ball onto rooftops or a higher route.
- Shield ("sticky coat"): the next bump knocks nothing off.
Pickups are claimed through the server (exists, not taken, in range, rate-limited), like absorbs. Effects end with the run. Boosters are never sold (constitution V).

### Traps and hazards (cartoonish, kind; constitution IV)
Traps are season-neutral kit items with a mechanic, and each theme dresses them through data (like the dressing slots in docs/design/01-world-kit.md), so Sunny City in January has the same traps as Holiday City:
- Slick patch: slippery, low control (winter: ice patch; city: spilled water or oil-free "wet floor" puddle).
- Bumper post: bounces the ball and knocks off stuck objects (the existing knock-off rule). A real street object (bollard), not a cartoon bumper.
- Slow patch: slows the ball for a moment (winter: slush; city: wet sand or fresh tar).
- A roaming street vehicle that bumps balls it touches (proposed: a street sweeper). Not the snowplough: in Holiday City a parked snowplough is an absorbable tier 4 overlay object, and the same model must not be both.
No damage, no deaths, no persistent loss: the worst case is losing stuck objects, which can be re-collected. Design rule: knock-offs are "a little jackpot", never a punishment (docs/design/03-city-level.md "Cascades").

### Marker spots
Booster and trap spots are placement markers in world data (a marker kind in WorldDef, Lune-validated), so 004e can place them in Downtown and theme overlays keep them clear. Snow Village gets markers for the grey-box check.

### Tricking other players in the default mode (owner decision needed)
- Proposed: ball-to-ball bumps knock objects off the smaller ball (like hitting an obstacle; the bigger ball is unaffected). Swallowing stays out of the default mode (constitution IV; it lives in 009).
- Optional: droppable traps (pick up a slick patch, drop it behind you). Plan decides if it is in.
- Either may change the maturity questionnaire answers ("cartoon bumping"), so the owner approves before work starts.

### Tests
- Lune: jump height from diameter at fixed diameters, booster durations and the boost cap, trap knock-off counts, marker validation.
- Jest-Lua (Studio): a booster pickup is refused when taken, out of range or over the rate limit; the speed check accepts a boosted speed within the cap and corrects one above it; jump spam is refused; remotes take only intents and IDs.

### Acceptance
- At every tier the ball can hop over an obstacle it cannot absorb yet (measured in a Studio run).
- Each booster and trap works in a Studio playtest behind its flag, in both the winter and city dressing; no new console errors or warnings.
- Grey-box check (constitution I): an agent-driven Studio run plus the owner playing it, recorded in playtest.md. No outside players (owner decision, 2026-10-26; people test this in 004d).

### Open questions (owner)
- Ball-to-ball bumps in the default mode: yes or no.
- Droppable traps: in or out.
- Charged jump: in or out.
- The starter booster set, and the roaming vehicle (street sweeper proposed).

## spec: 004c: Juice pass: animation, VFX and game feel
<!-- id: 4d4e47f5 -->

Make Rollossal look and feel like a game before outside people play it (owner, 2026-10-26: people come in "when we have some graphics and animation and the game looks like a game"). Mechanics are already grey-boxed in 001–004b, so this is the polish constitution I allows after them. Design brief: docs/rollossal-gdd.md §5 (art and audio direction); design system: docs/design/README.md (Motion), 05-roblox-limits.md ("Motion is client-side and rare"), 04-player-cosmetics.md (performance per ball). Constitution: I, VI (budgets), VII (flags where behaviour changes; theme effects are data), IX (every effect has a visual and a non-colour cue). Depends on 004a (themes), 004b (jump, boosters, traps) and 004e (Downtown, Holiday City art and audio).

### Ball
- Squash and stretch on landing and hard bumps; a slight wobble of stuck objects as the ball rolls.
- A ground trail and puffs that grow with the ball, taken from the active theme (winter: snow; city: dust), never hard-coded to snow.
- A rolling sound whose pitch and volume follow speed and size.
- Stuck objects "stick" with a tiny pop and settle into the surface rather than snapping.

### Pickups and growth
- Pickups pop (scale 1 → 1.15 → 1 over `Config.growTime` 0.25 s), the HUD size number rolls up, the size bar eases.
- The default pickup burst is built as the default "pickup effect" so 006a can swap it per player; the pitch-rising pickup sound keeps its volume when timbres change.
- Tier-up moment: a short slow-down, camera pull-back, fanfare and a banner animation (banner holds 2.5 s); the next tier's hero prop is highlighted once.
- Knock-off: objects scatter with bounce and a brief shake (removed by Reduce motion). Cascades (Pizza Box Tower, fruit pallets, the Vending Machine dropping cans) spill when hit.

### World
- Hero motion, client-side only and within 200 studs of the camera, as a `RenderStepped` tween on a child part, flagged in object data: the swaying Tube Guy, the turning donut on the Donut Food Truck, the spinning office chair, the Ferris Wheel. No server-replicated animation.
- Ambient pigeons (at most 8 per district) that flap off when a ball comes near; never absorbable. No other animals.
- Booster and trap visuals from 004b: readable from far away on a phone, each with an icon and a label in the HUD when active.

### UI
- Results screen celebration (stars landing one by one, coins counting up), button press feedback, screen transitions, using the UI tokens in docs/design/tokens.md.

## spec: 005: Co-op: merge and split, friend bonus, party flow
<!-- id: 89459d21 -->

Make Rollossal funny with friends: two friends can merge into one bigger ball, steer it together, and split again; friends earn bonus coins; parties start and repeat runs together. Design brief: docs/rollossal-gdd.md §1 (pillar 2), §3.4 (multiplayer), §4 (Merge button); design system: docs/design/tokens.md (touch sizes). Constitution: II, III, IV, VI, VII (behind a flag). Depends on 002 and 003.

### Rules (src/shared/Rules, Lune-tested)
- Merge: the merged ball's volume is (V1 + V2) × 1.10 (merge bonus 10%, proposed, in Config).
- Split: each player takes half the merged volume.
- Exploit to close: merging and splitting repeatedly would grow both balls by 10% per cycle without rolling anything. The spec must prevent this. Proposed: the bonus applies once per pair per run, plus a merge cooldown (about 10 s). The tests prove that any number of merge-and-split cycles adds at most one merge bonus per pair per run.
- Coins earned while merged are split evenly; the rounding rule is defined and tested.
- Coin multipliers: friend bonus +20% while at least one Roblox friend is in the server (proposed). Its order with 2x Coins and Friend Boost (006b) follows the coin rule defined in 002.

### Merge flow
- The Merge button (bottom right, at least 96 px, `touch-main`) appears only while touching an eligible player. Both players must tap it within a short window (proposed 3 s); the server checks both requests, the touching distance and the cooldown.
- Eligible: Roblox friends and members of your party (proposed). Strangers cannot merge with you, so nobody can be pulled into a merge.
- Steering is the average of both players' inputs. The plan decides who simulates the merged ball (one player's client owns it and receives the partner's input through the server, or the server owns it) and measures input latency on a phone.
- Absorbs, knock-offs and tiers work as for a single ball. Each player gets every new book entry the merged ball collects (proposed).
- Cosmetics on a merged ball (once 006a lands): the plan decides whose skin shows and how both players' toppers and trails appear (proposed: the bigger contributor's skin; both toppers side by side; both trails), within the per-ball performance budget in docs/design/04-player-cosmetics.md.
- Split: either player taps Split; both balls reappear side by side with half the volume each.
- Timers stay personal. When one player's run ends while merged, the ball splits automatically: that player goes to results, the other keeps playing.

### Party flow
- Invite friends with the built-in Roblox invite prompt (`SocialService`); no typing or chat needed.
- A party starts its runs together with one shared timer, and Roll again keeps the same friends together (docs/rollossal-gdd.md §2: "same friends, about 3 seconds").
- The results screen shows the party's sizes side by side.

### Tests
- Lune: merge and split maths, the once-per-pair bonus, coin splitting and rounding, multiplier order.
- Jest-Lua (Studio): merge needs both players' consent; is refused when not touching, during cooldown or for non-eligible players; remotes accept only intents (no sizes); a player leaving while merged splits the ball cleanly and loses nothing.

### Acceptance
- Two friends can merge, roll up objects together, split, and each keeps half; repeated merge and split cannot inflate size.
- A party of 3 can play three runs in a row with Roll again and stay together.
- Merge and Split are playable with one thumb on a phone (the owner checks on a real phone).
- Behind a feature flag in Config; no new console errors or warnings in a Studio playtest with at least 2 clients in Downtown.
- Grey-box check of merge before any polish (constitution I): an agent-driven Studio local server with 2 or 3 clients plus the owner playing it, recorded in playtest.md. No outside players are needed for this feature (owner decision, 2026-10-26); merging with real friends is covered by the next people playtest round (004d if 005 lands before it, otherwise the pre-launch round in 008).

### Out of scope
Big Ball mode and player swallowing (009); the Friend Boost game pass purchase (006b; its +25% effect for everyone in your merged ball is applied by the coin rule here once 006b reports ownership).

### Open questions (owner)
- Merge with non-friends in the same server: allow or not (proposed: friends and party only).
- Do both merged players get book entries (proposed: yes)?

## spec: 009: Big Ball mode: opt-in player swallowing
<!-- id: 2e3ef672 -->

After launch (planned for late December): an opt-in mode where a ball 1.3× bigger than another player's ball can swallow it. Never on in the default mode. ### Mode
- Lives in its own servers (a separate place in the universe, or reserved servers; the plan decides). Players enter only through an explicit choice in the hub with a short explanation of the rules. Never on in the default mode, never a surprise.
- Rule (src/shared/Rules, Lune-tested): a ball can swallow another when its diameter is at least 1.3× the other's (proposed, in Config). Whether the swallower gains the victim's volume, and how much, is defined in the spec (proposed: like an object, with the growth efficiency k).
- The swallowed player respawns small at once, with brief spawn protection (proposed 3 s), and loses no permanent progress: coins and book entries already earned in that run are kept.
- The server validates every swallow (both balls exist, distance, the 1.3× rule, the victim is not protected).
- Fairness: ball cores never apply here; nothing paid changes the outcome (skins, toppers, trails, auras and effects are cosmetic; 2x Coins only affects coins after the run). Merging is disabled in this mode (proposed) to avoid teaming.
- Kind design: no kill feed naming players, no taunts; a per-server "biggest ball" board only. The swallow is shown as the ball rolling the other up, never as harm (no absorbable people; the avatar, if 010 is on, is not shown being swallowed).
- Behind the `BigBallMode` feature flag.

Unlike the personal runs of the default mode, Big Ball rounds are shared matches with one server timer, so everyone starts and ends together:
- Peaceful phase (proposed first 60 s of a 4-minute round): no swallowing; everyone eats objects and grows. A clear banner and sound announce when it ends (and the HUD shows when swallowing switches on, with an icon and label, not colour alone).
- Swallow phase: the 1.3× rule is live. Boosters and traps from 004b work here too, so a smaller ball can escape or trick a bigger one (for example a dash, a shield or luring it onto a slick patch).
- Hill (optional, plan decides): in the last minute a marked zone (proposed: Downtown's Plaza) gives bonus growth to the biggest ball standing in it, so the round ends in a fight for the hill rather than hiding. The hill is a marker in world data, not code.
- The biggest ball at the bell wins the round; the results show the top three sizes, no names in a feed.
- The Rules for phases (which phase is live at time t) are pure functions with time passed in, Lune-tested.

### Tests
- Lune: the swallow threshold at the boundary, volume gained, phase at a given time (peaceful vs swallow vs hill).
- Jest-Lua (Studio): a swallow request is refused below 1.3×, out of range, against a protected player, or during the peaceful phase; a swallowed player keeps their coins and book entries; the default mode never allows a swallow even if a client asks.

### Acceptance

Real players try it in the next people playtest round (owner decision, 2026-10-26: no outside players before the game has art and animation).

## spec: 012: Live ops: weekly object drops and the daily golden object
<!-- id: dc2bd70f -->

After launch: weekly content drops in December (8–10 new objects and one new skin per week), the daily golden object, and a weekly golden-object event, all shipped as data. Design brief: README.md §3.5 (daily golden object), §7 (live ops). Constitution: I (the owner's grey-box sign-off; the playtest with outside people is in 004d, owner decision 2026-10-26), III, IV, V, VII, VIII. Depends on 003 and 004.

### Weekly object drops
- New objects are content data plus assets; no code changes. Each object can carry an `availableFrom` date, so a drop can ship ahead of time and switch on by server date (the date is passed into pure Rules, never read inside them).
- Drops extend the collection book; page progress and page rewards stay correct when a page grows (a completed page that gains entries does not take its reward back).
- A short how-to in the feature folder: the steps to add a drop (Blender, budgets, Assets.luau, content entry, localisation in English and Spanish, validation tests).
- New objects stay in the game after their week: nothing becomes missable forever (pillar 4, "nothing pressures you").

### Daily golden object
- One hidden golden object per world per day, chosen and placed by a seed derived from the UTC date (pure function in src/shared/Rules, Lune-tested: the same date always gives the same choice and spawn point).
- Absorbing it gives bonus coins (value in Config) once per player per day. The server validates it like any absorb.
- Missing a day costs nothing: no streaks, no countdowns, no reminders.
- Storing "claimed today" in the profile is a schema change: owner approval and a migration with a test (constitution VIII).

### Weekly golden-object event
A weekly variant (for example several golden objects for a weekend) defined as dated content data, using the same mechanism.

### Weekly skin
One new cosmetic skin per week through the shop from 006. Each new product and its price needs owner approval.

### Acceptance
- Adding a drop is a data and asset change only; scripts/check.sh exits 0 with the new content.
- The golden object appears in the same place for every server on a given day and can be claimed once per player per day.
- No new console errors or warnings in a Studio playtest.

### Open questions (owner)
- The golden object's coin bonus.
- Approval for the profile field that tracks the daily claim.

## spec: 004a: Theme system and stylised-real art pipeline
<!-- id: 2a4da119 -->

Part 1 of the Downtown work (docs/design/speckit-prompt.md, split as it suggests): the season-theme system and the art pipeline that every later world, theme and prop is built on. No Downtown content here; that is 004e. Design: docs/design/01-world-kit.md (Patterns 1, 2, 2b, 3, 5), 06-art-style.md, 05-roblox-limits.md, tokens.json. Constitution: VI, VII, XI. Depends on 004 (content model, Blender pipeline).

### Why
Long term the first level is one city re-themed by season instead of a new map per season. One map keeps the small launch player base together in full 12-player servers, halves pacing and balance work, and makes every later season (January Sunny City, spring, autumn, night) a data change.

### Prerequisite (owner, before /speckit-plan)
A constitution amendment to principle XI, through /speckit-constitution: smooth shading allowed on round parts with one bevel segment on silhouette edges; "one palette texture" becomes "one gradient atlas per theme, all with the same layout"; ball skins (006a/006b) may use their own 512 px texture. Until it lands, speckit-analyze flags this feature against XI.

### Theme (content data, constitution VII)
A theme is `{ id, paletteAsset, lighting, weather, music, slots = { [slotId] = objectId }, overlays = { zones, fixedPlacements }, heroVariants = { [objectId] = assetKey }, bookPage }`:
- A palette atlas with a fixed layout. The client swaps `MeshPart.TextureID`; stand-in parts take `Part.Color` from the same palette role, so grey-box layouts already show the season.
- A lighting block (clockTime, brightness, fog, atmosphere from `light-sky`, `light-fog`, `light-ambient`), one camera-attached weather `ParticleEmitter` (max 40 particles, off with Reduce motion) and a music track.
- Dressing slots: placements whose object depends on the theme (`slot.small`, `slot.medium`, `slot.yard`, `slot.street`, `slot.landmark`). Dressing stays under about 15% of placements.
- Optional overlays: extra zones and fixed placements only that theme adds. They count in the level's placement budget, never block ring gates, shortcuts or landmark sightlines, and must pass the same pacing check.
- Optional hero variants: a base hero mapped to an alternate mesh with the same tier, size (±10%), collision class and coins.
- Its own collection-book page for theme-only objects. The page returns with the theme every year and is never "limited"; while the theme is off it stays visible with progress kept, marked as returning.
The world picks its active theme by id in data. Switching is a content change and a release, never code and never a date check (owner decision 2026-10-28; no countdown to players, constitution V).

### Themes defined here (tokens only, no props)
`city` (Sunny City), `winter` (Holiday City), `spring`, `autumn`, `toon`, `neon`: palette (all 64 cells) and lighting from docs/design/tokens.json. Props and dressing for `winter` and `city` come in 004e.

### Stylised-real art pipeline
- One 1,024 px gradient atlas per theme, generated by script from tokens.json: 64 palette cells (128 × 64 px, vertical gradient +12% to −15% lightness) on top, 8 trim strips (1,024 × 64 px) below. `art/scripts/palette.py` becomes this generator.
- `export_all.py` allows split normals; the UV rule becomes "every face inside one atlas cell or one trim strip"; one material per mesh.
- The Blender MCP recipes add one bevel modifier (about 4–8% of object size), applied before export.
- `RenderFidelity = Automatic` on every MeshPart. No SurfaceAppearance/PBR, no transparency (water and glass are opaque swatches), no per-prop lights (glow is `Material.Neon` on a child part, tier 4–5 heroes only). CollisionFidelity Box for tiers 1–3, Hull for 4–5.
- Rows 0–3 are shared roles, rows 4–7 belong to a level's heroes. A palette QA grid renders a prop in every theme.

### Budgets (owner approval)
`Config.Budgets.meshTriangles` from 300/300/800/2500/2500 to the proposed 500/700/1500/3500/5000. The new numbers go in behind this feature; they are locked only after 004e's measured capture on the reference phone at full density with 12 balls and the Holiday overlays.

### Proof without Downtown
Re-theme an existing world (Snow Village or a small test layout) between `winter` and `city` by changing only the active theme id: palette, lighting, weather, music, one slot of each kind, one overlay and one hero variant switch over, and the base layout stays the same.

### Tests
- Lune: every theme fills every palette role and every slot the world declares; overlays stay inside the placement budget and clear of gate, shortcut and sightline areas; every hero variant matches its base's tier, size (±10%), collision class and coins; theme ids unique.
- Lune or a script check: the atlas generator is deterministic and its layout matches the token roles.
- Studio: a theme switch is a data-only change; no new console errors or warnings.

### Acceptance
- Two themes load from one base layout and switch by data only.
- The atlas generator and export checks run in `scripts/check.sh` (or the art pipeline's own check) and pass.
- 30 fps unchanged on the test layout in a 640 × 360 capture.

### Open questions (owner)
- Approve the XI amendment wording.
- Approve the proposed triangle budgets as provisional until 004e's capture.

## spec: 004e: Downtown, the launch world in its Holiday City theme
<!-- id: 3855b0b1 -->

Part 2 of the Downtown work (docs/design/speckit-prompt.md): Downtown, the first city level, launching in December as Holiday City and switching to Sunny City in January. It replaces Snow Village as the launch world. Design: docs/design/02-city-assets.md, 03-city-level.md, 07-holiday-city.md, 05-roblox-limits.md, 06-art-style.md. Constitution: IV, VI, VII, IX, XI. Depends on 004a (theme system, atlas pipeline) and 004b (marker spots for boosters and traps).

### Why
The game will most likely be ready around 2026-12-01, so the launch world must be a Christmas map. Launch players are age-checked 16+ during the trial, so props look like real city objects with one absurd twist each, festive but never cute or babyish.

### World (content data)
- A new world, Downtown. Snow Village stays in the code only as the Config rollback path, like GreyBoxRoom; `DefaultWorldsUnlocked` and the default world move to Downtown. Snow Village's cat and dog are retired with it (no absorbable animals).
- Reuses the WorldDef shape, `Layout.expand` zones, fixed placements, spawn points, the hub and the 600 × 600 envelope (halfExtent 300, outer 400).
- 12 doorstep spawns; about 1,400 placements in total, theme overlays included (rough split by tier 480/380/280/180/60).
- Five tiers with the current minimum diameters 2/5/12/30/70 and absorb ratio 0.4: Pocket, Sidewalk, Street, Block, Skyline. A core kit of 74 absorbable object types, 2–3 hero props per tier, all season-neutral (every top face uses `w-season`).
- Layout in rings matching the tiers: Stoops and Alleys (spawns, 40 Pocket objects within 10 studs of each spawn), Sidewalks, then the Park, the Construction Site and the Car Park, then Market Street and the Plaza, then the Skyline Block and the Waterfront.
- Each ring is gated by objects one tier up. Narrow alleys (4 studs) and a storm-drain tunnel are shortcuts only tier 1–2 balls fit through. Heroes sit on sightlines, and every spawn can see a tier 5 landmark.
- Something to climb: the Car Park spiral ramp and the site's scaffolding and container stack; kerbs and stoops need the jump at tier 1 (jump from 004b).
- Marker spots in data: the booster and trap spots from 004b, and the seeded golden-object hiding spots for 012 (bus-shelter roof, car park top deck, drain tunnel, crane counterweight, behind the Ferris Wheel). Overlays keep them clear.
- `cullTierDelta` 2 stays; respawns 60–120 s out of sight refill the doorsteps.

### Pacing (4:00 run)
First pickup by 0:05, tier 2 by about 0:30, tier 3 by about 1:30, tier 4 by about 2:45; 3 stars (80) means reaching tier 5. Checked by an agent-driven bot run (AGENTS.md "Driving the ball") within ±20 s, in every theme that ships (winter and city).

### Holiday City (`winter`, the launch theme, full art)
- Winter palette, golden-hour lighting (clockTime about 16.5), snowfall, a holiday music track (owner picks).
- Slots: bauble, gift box, snowman, sleigh, and the Mega Tree as the Plaza landmark.
- Overlays (about 150 placements, taken from slot and tier 1–2 counts): a Christmas market of 6 stalls, a cocoa cart and a gift pile around the Mega Tree; garlands on Market Street; fairy-light bulbs, baubles and mini gifts at the doorsteps; a sledding slope and an ice rink in the park; snow piles and a parked snowplough at the edges.
- Hero variants: the Cocoa Truck (for the Donut Food Truck) and the bow-wrapped Glass Tower.
- The 20 holiday objects in 07-holiday-city.md. No elves, plush or cartoon Santa; the reindeer is a light-up wire decoration. Book page "Downtown: Holiday".

### Sunny City (`city`, needed by January)
Palette, lighting and its slot dressing (ice lolly, beach ball, paddling pool, ice-cream truck, Giant Inflatable Duck). It may ship with palette and lighting only if the dressing is late; the dressing then finishes in 011.

### Art (stylised real, pipeline from 004a)
Every core, hero and holiday mesh through Blender: real proportions, one bevel segment, smooth round parts, one atlas cell or trim strip per face, one material, within the tier's triangle budget. Ground, roads and kerbs are Parts with SmoothPlastic and a `w-*` colour; no Terrain. Downtown loads with stand-in parts before any art exists, so layout and pacing can be tuned first (constitution I).

### Content rules (constitution IV)
No absorbable people or live animals (pigeons are ambient, at most 8 per district, and fly off). No weapons, alcohol-like bottles, gambling imagery, real brands, flags or landmarks, and no words on textures (pictograms only). Vehicles never crashed, burning or upside down. Every object name is a localisation key in English and Spanish.

### Tests
Lune: unique ids, sizes ascending by tier, every slot filled in every defined theme, every palette role present in every theme, overlays inside the placement budget and clear of gate, shortcut, marker and sightline areas, every hero variant matches its base.

### Acceptance
- Downtown loads with stand-in parts, then with meshes.
- Holiday City and Sunny City both load from the same base layout; switching is data-only.
- 30 fps on the reference phone at 640 × 360 with 12 balls in Holiday City (the heaviest theme); the triangle budgets from 004a are locked from this capture.
- Active parts stay under `Config.Budgets.maxActivePartsPerServer` (2,000).
- The pacing targets are hit in bot runs in both themes.
- Grey-box check of the layout before art (constitution I): agent bot runs plus the owner playing it, recorded in playtest.md.

### Out of scope
Ball skins, toppers, trails and the shop, including holiday cosmetics (006a/006b). Co-op merge (005). The people playtest (004d). Art for spring, autumn, toon and neon. Store icon and thumbnails (008).

### Open questions (owner)
- The holiday music track.

## spec: 006a: Cosmetics and the coin shop: five equip slots, unlocks and rewards
<!-- id: ec41418f -->

Everything a player can show off, bought with coins earned by playing or unlocked by play. This is the coin sink the economy (003) does not have yet. Robux items and receipts are 006b. Design: docs/design/04-player-cosmetics.md, 05-roblox-limits.md; docs/rollossal-gdd.md §4 (Shop screen), §6. Constitution: I (owner's grey-box sign-off), IV, V, VI, VIII, IX, XI. Depends on 003 (profile, coins, book) and 004e (Downtown book pages).

### The design problem
From about 30 seconds in, stuck objects cover the ball and it is always rolling. A skin alone disappears exactly when the player is proudest, and a face painted on a skin spins upside down. So mid-run identity lives in the topper, trail and aura, and anything with a face is a set (all-over skin plus an upright topper).

### Equip slots
Skin, Topper, Trail, Aura, Pickup effect. A set is a skin and topper sold or earned together. Others see your loadout. All cosmetic, never stats.
- Skins: a sphere MeshPart with one 512 px texture per skin (sports balls share one UV layout), or a built-in Material + Color. Needs the XI amendment from 004a.
- Toppers: hover above the ball, upright, never rolling, scale with diameter, bob at most 0.2 × diameter (Reduce motion stops it); ≤ 300 tris, palette atlas only.
- Trails: a `Trail` on a non-rotating follower, `WidthScale` grows with diameter. Pooled-piece trails keep at most 20 pieces per ball, fade in 2 s, never collide.
- Auras: ParticleEmitters around the ball, scaled with diameter.
- Pickup effects: replace the default pickup burst from 004c and change the pickup sound's timbre, never its volume.

### Launch set (proposed)
Skins (10): Rubber (default), Football, Basketball, Tennis Ball, Baseball, Chrome, Galaxy, Disco, Pixel, Eight-Ball. Toppers (5): Traffic Cone, Crown, Googly Eyes, Banana for Scale, Signal Bars. Trails (6): Rainbow Lane, Light Cycle, Drift Sparks, Caution Tape, Toilet Paper, Tyre Skids. Auras (3): Orbit Rings, Spark Field, Pixel Bits. Pickup effects (3): Confetti, Pixel Shatter, Comic Burst. The creature sets (Kitten Ball, Pupper Ball) and the holiday season pack are Robux items in 006b. Plan may trim the set to fit the launch date; the slot system ships whole.

### Unlocking (constitution V)
- Coins (earned by playing only): sports balls, most material skins, toppers, trails, auras, effects. Coin prices are tuning values the owner confirms.
- First time reaching a tier: the world's `sizeTiers[n].reward`.
- Completing a collection-book page: a topper per page; the Golden skin for the full Downtown book (never sold).
- Never: random boxes, rarity colours, countdowns, "limited" stock, pop-up offers during a run.

### Shop screen
Tabs: Skins, Toppers, Trails, Auras, Effects (Passes arrives with 006b). Closed during a run (TopBar shows "after this run"); introduced from run 2 (007). Tiles on `ui-card`, a static icon, name in `body`, a "what it does" line in `small`, the price button; the selected tile has a 3 px `ui-highlight` ring; owned items show Equip. One ViewportFrame previews the selected item with the full loadout, never one per tile. Touch targets and text sizes per docs/design/tokens.md.

### IP and safety
Use the idea, never the image, name or music: no meme images, real logos, league or maker designs, or real faces (the keep-out list in 04-player-cosmetics.md). Nothing mocks a group of people.

### Performance budget per ball
Own ball: 1 trail, 2 particle emitters with ≤ 30 particles alive, 20 pooled pieces. Other balls: 1 trail and emitters at half rate, both off beyond 150 studs, 10 pooled pieces. Reduce motion: particles and topper bob off; flat trails stay. Checked with 12 balls at tier 4 on the reference phone.

### Profile (constitution VIII, owner approval)
Owned items per slot and the equipped item per slot replace today's skin-only fields: a schema change with a migration and a test.

### Tests
- Lune: unlock rules (coin balance, tier reward once, page reward once, Golden skin on the full book), coin prices from data, never below zero.
- Jest-Lua (Studio): buying with coins is server-validated and idempotent per request; equipping an unowned item is refused; the migration keeps existing skins.

### Acceptance
- Every launch item equips and shows correctly on own and other balls in a 12-client Studio run; 30 fps holds.
- The shop reads at 640 × 360 in English and Spanish.
- No new console errors or warnings.

### Open questions (owner)
- Coin prices.
- Approval for the profile schema change.
- The final launch set if time is short.

## spec: 013: Second level and level select: coin unlocks and the early unlock product
<!-- id: f81db43f -->

After the January switch, once the player base can fill servers in more than one map: the second city level built from the shared kit, plus the level select and unlocking levels with coins. Moved here from the old 011 (Candy Town), which the design replaced with one city re-themed by season (docs/design/01-world-kit.md). Design: docs/design/01-world-kit.md ("Reusing it for new levels"), 05-roblox-limits.md; docs/rollossal-gdd.md §3.5, §6. Constitution: V, VII, VIII, XI. Depends on 004a, 004e, 006b (receipts) and 011.

### The level (data and assets only, constitution VII)
- A new level reuses the core kit (about 70% of placements), adds 8–12 hero props in palette rows 4–7, and runs in every theme the active season defines. Candidates from the design: Beach Boardwalk, Suburbs, Airport (owner picks).
- If anything needs a code change to add it, that is a defect in the content model: fix it in its own task, with a test.
- Same pacing check as Downtown (bot runs within ±20 s), its own book pages, best size kept per level.
- Never babyish: real places with one absurd twist, no nursery sweets or plush.

### Level select and unlocks
- The hub gets a level select: name, best size and unlocked state.
- Downtown is free. The next level is unlocked with coins (a tuning value the owner confirms); unlocks are stored in `worldsUnlocked`.
- Early unlock (developer product): unlocks the next level now; also earnable with coins. Owner approval for the product and price (constitution V); 006b's receipt handler grants it idempotently.
- The plan decides whether levels are separate places in the universe or one place loading a level's content, and justifies it against keeping servers full.

### Acceptance
- The level is playable end to end in at least two themes with no level-specific code.
- Unlocking with coins works once and survives rejoining; the early unlock grants once.
- 30 fps on the reference phone at tier 4 with 12 balls.
- No new console errors or warnings.

### Open questions (owner)
- Which level, and when (depends on launch player numbers).
- Coin price and the early-unlock product price.
